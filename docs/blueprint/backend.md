# 股票行情與指標系統 — 整合系統藍圖

## 1. 文件目的

本文件整合四份 backend spec——`stock-price-ingestion`（股票行情抓取與回補）、`stock-indicator-statistics`（MACD／KD 指標運算與統計）、`stock-catalog`（股票清單查詢）、`stock-minute-price`（分 K 隨選抓取與查詢）——描述整合後系統**現在**的樣子，而不是逐一介紹每份 spec 做了什麼。

系統現在是一條完整的資料鏈：股票主檔與日線行情由排程與**應用程式啟動時的自動補齊**共同維護 → 日線行情批次結束後**自動接著**觸發全市場指標重算 → 使用者透過股票清單找到個股、在日 K 圖上點選特定交易日時才**隨選抓取**分鐘 K 棒。整條鏈路中，只有分 K 抓取由使用者操作觸發，其餘兩段（日線補齊、指標重算）在系統啟動完成後即自動於背景執行，不經過任何對外端點，也不會讓應用程式啟動變慢或失敗。

## 2. 全景關係圖

![Diagram 1](backend/1.png)

六個資料實體：**股票主檔**是全市場代號、名稱、是否在市的唯一權威來源，向外連到日線行情、同步進度紀錄、分鐘 K 棒三者。**日線行情**是系統唯一的行情事實來源，向下推導出**指標**、也是分鐘 K 棒查詢用來核對「這天是不是交易日」的依據。**同步進度紀錄**是行情回補與指標重算共用的追蹤表。**分鐘 K 棒**與**分 K 抓取狀態**是隨選抓取模組的一組資料。

## 3. 各資料實體說明

### 3.1 股票主檔

<img src="backend/1-stock.png" width="320" alt="股票主檔在全景圖中的位置">

*（節錄自完整架構圖）*

全市場（上市、上櫃）股票的代號、名稱、市場別、是否仍在市的唯一權威來源。它不是由獨立資料源維護的——交易所每日快照本身就同時帶回代號與名稱，因此每次每日增量更新或回補都會順帶把它補齊，不需要另一套抓取邏輯。全景圖中另外三個實體（日線行情、同步進度紀錄、分鐘 K 棒）都以它的代號為依附主體。它的寫入行為已包含在下方「日線行情」的詳細圖中，不再重複繪製。

詳細欄位、規則與 API 定義 → docs/backend/stock-price-ingestion.md、docs/backend/stock-catalog.md

### 3.2 日線行情

<img src="backend/1-price.png" width="320" alt="日線行情在全景圖中的位置">

*（節錄自完整架構圖）*

全市場逐日開高低收與成交量的落地表，是整個系統唯一的行情事實來源——指標運算不另外對外抓取，分鐘 K 棒查詢也用它來判斷某一天是否為交易日。由三條路徑共同寫入：例行的「每日增量更新」（單一請求涵蓋全市場）、手動觸發的「回補」（指定多檔或全市場，逐檔查詢歷史）、以及**應用程式啟動完成後自動觸發的「啟動補齊」**。這三者共用同一套速率控制、重試退避與寫入邏輯，啟動補齊並非另一套實作，只是以「全市場、依進度接續、迄日為今日」的參數呼叫既有的回補路徑。停牌或無交易的日期不補零，直接不產生該筆列。

![Diagram 2](backend/2.png)

啟動補齊的關鍵行為：「應用程式啟動完成」是一個新增的觸發來源，不經過任何對外端點，在背景把每一檔在市股票從它自己的進度接續補到今日；補齊在背景執行，絕不讓應用程式延後可服務、也絕不因外部來源失敗（離線、逾時、被限流）而讓啟動失敗，失敗的標的落入既有的重試流程。此機制由同一個設定開關控制（預設啟用，可停用供測試與離線開發使用），且判斷「要不要抓、從哪天抓」的依據是**每檔已同步到的日期與目標迄日的差距**，而不是該檔目前的完成狀態——這與「續傳」是兩件不同的事：續傳只挑還沒完成或失敗的檔，一檔已完成但進度落後（例如上次只補到上週）的股票，續傳永遠不會再碰它；啟動補齊看的是日期差距，因此會把它重新開啟、只補上落後的那一段。

詳細欄位、規則與 API 定義 → docs/backend/stock-price-ingestion.md

### 3.3 MACD／KD 指標

<img src="backend/1-indicator.png" width="320" alt="MACD／KD 指標在全景圖中的位置">

*（節錄自完整架構圖）*

由日線開高低收推導出的 MACD 與 KD 遞迴指標，連同暖身區間（讓遞迴指標收斂所需的前置運算天數）的標記一起落地儲存，供統計查詢直接讀取，不現場運算。全量重建與每日增量共用同一套公式，增量模式只需前一交易日的遞迴狀態與最近幾日的高低價，成本與歷史長度無關。行情已回補但指標尚未重算是完全正常的中間狀態，統計查詢以日線行情為主、指標為外連接，讓這種狀態下的日 K 圖仍能顯示行情，只是指標欄位是空的。

![Diagram 3](backend/3.png)

啟動後的自動重算：日線行情的啟動補齊批次**全部結束之後**（不與其並行，避免依據不完整的行情算出之後還要重算一次），系統自動以「增量」模式對全市場觸發一次指標重算，不需要任何人手動觸發。它與行情批次由**同一個設定開關**控制、共用重算服務與進度追蹤，但使用不同的作業類型，因此兩者的併發鎖互不影響；同樣在背景執行、不阻塞啟動、單檔失敗不影響應用程式本身。

詳細欄位、規則與 API 定義 → docs/backend/stock-indicator-statistics.md

### 3.4 同步進度紀錄

<img src="backend/1-progress.png" width="320" alt="同步進度紀錄在全景圖中的位置">

*（節錄自完整架構圖）*

橫跨「行情回補」與「指標重算」兩種作業類型共用的斷點續傳與併發控制表，記錄每一檔股票在每種作業下目前的進度狀態（待處理／執行中／完成／失敗／略過）、已同步到的日期、以及嘗試次數。它是回答「資料何時能追上今日」的依據：續傳依狀態判斷，補齊依已同步日期與目標迄日的差距判斷，兩者的差異已在上方「日線行情」小節說明。同一時間同一種作業類型只允許一批次執行，是避免兩批寫入交錯損壞資料序列的保護機制。

詳細欄位、規則與 API 定義 → docs/backend/stock-price-ingestion.md、docs/backend/stock-indicator-statistics.md

### 3.5 分鐘 K 棒

<img src="backend/1-minute.png" width="320" alt="分鐘 K 棒在全景圖中的位置">

*（節錄自完整架構圖）*

某檔股票在某一個交易日的分鐘級開高低收與成交量。與日線行情的排程式全市場抓取刻意不同，分 K 採**隨選抓取**：使用者在日 K 圖上點選某一天時才向外部來源查詢，成功後永久落地，之後同一組合的查詢一律為純資料庫讀取，不重複對外請求。外部來源只提供最近 30 天的分鐘資料，超出視窗的舊日期一律無法補抓，這是產品層級的限制，會誠實地反映在查詢結果中，而不是偽裝成暫時性錯誤。

![Diagram 4](backend/4.png)

詳細欄位、規則與 API 定義 → docs/backend/stock-minute-price.md

### 3.6 分 K 抓取狀態

<img src="backend/1-fetch-status.png" width="320" alt="分 K 抓取狀態在全景圖中的位置">

*（節錄自完整架構圖）*

記錄每一組（股票、交易日）分 K 抓取結果與嘗試次數的狀態表，是每次查詢決定「這次要不要真的對外部來源發出請求」的依據——已知超出 30 天視窗、已確認查無資料、或已失敗達重試上限的組合，一律直接回覆已知結果，不再對外部發出注定失敗的請求。

詳細欄位、規則與 API 定義 → docs/backend/stock-minute-price.md

## 4. 通用／可重用模組

- **速率控制與重試退避機制**：由行情抓取模組建立（可設定的請求間隔、對限流與逾時的指數退避重試），分 K 隨選抓取直接重用同一套機制，不另外實作一份。
- **同步進度與併發鎖（作業類型化）**：同一張「同步進度紀錄」表同時服務行情回補與指標重算兩種作業，靠作業類型欄位區分彼此的進度與併發鎖，不需要為每種作業各建一張表。
- **啟動自動化開關**：單一設定開關同時控制「啟動時自動補齊行情」與「行情補齊完成後自動重算指標」兩個階段——關閉時兩階段都不會觸發，開啟時兩者依序自動接力，不需要分別設定。

## 5. End-to-End 情境走查

**情境一：全新環境從開機到日 K 圖可用的完整時間線**
資料庫剛完成重置，只有股票主檔、完全沒有任何行情與指標。應用程式啟動完成的瞬間，後端立即在背景以「全市場、補齊起日、今日」的參數呼叫行情回補（此時應用程式已可正常回應股票清單等其他查詢）。行情逐檔依速率限制向外部來源取得歷史資料並落地，這段可能需要數十分鐘，期間任一檔失敗只影響該檔本身。行情批次全部結束後，後端自動以「增量」模式對全市場觸發一次指標重算。如果使用者在指標批次完成前就打開某檔的日 K 圖，會看到完整的 K 棒，但 MACD／KD 副圖是空的——這是行情與指標由兩個獨立作業寫入所產生的正常中間狀態，不是錯誤；等指標批次也結束後重新整理即可看到完整內容。

**情境二：開發機頻繁重啟，為什麼不會重複打外部 API**
一檔股票上次啟動已完整補齊到今日（進度為完成、已同步日期等於今日）。下一次重啟時，啟動補齊逐檔比對「已同步日期」與「目標迄日（今日）」，發現兩者相同，該檔完全跳過、不發出任何外部請求——這與「續傳」不同：續傳只挑還沒完成或失敗的檔，如果另一檔上週因限流被標記失敗且已達重試上限，用續傳重跑不會再碰它；但用啟動補齊的判斷邏輯（比對已同步日期而非狀態），這檔會被重新開啟，只補上落後的那一小段區間，且重試次數會歸零重新給予機會，因為落後是時間前進造成的，不是先前失敗造成的。另外，若某次以週六（非交易日）為目標迄日執行，系統會把「已同步到週六」這件事記錄下來，而不是記錄成最後一個實際交易日，這樣下一次啟動比對週六與目標迄日仍然相等，不會把「最後交易日到週末」這段空區間反覆重抓。

**情境三：同一天，日 K 有資料、指標還沒算完、分 K 又超出視窗**
使用者點開某檔 90 天前的一個交易日想看分 K：由於已超出外部來源 30 天的資料視窗，系統本地判斷後直接回覆「超出視窗」，不發出任何外部請求；但因為那天確實是交易日，仍會附上當天的日線摘要（開高低收與成交量），畫面不會一片空白。使用者接著點開 5 天前的交易日：系統向外部來源即時抓取並永久落地，之後任何時間再查詢同一天都是純資料庫讀取，即使將來這天超出了 30 天視窗也依然讀得到。若這兩天日 K 圖上的 MACD／KD 剛好還沒被指標批次算到，該狀態不影響分 K 是否能查——日線指標與分鐘 K 棒是兩個完全獨立維護的資料，互不牽動彼此的可用性。
