# 股票監控系統 — 整合資料架構藍圖

## 1. 標題與目的

本文件整合以下 8 份 backend spec，統一畫出「這個系統現在長什麼樣子」，而不是逐一介紹每份 spec 在做什麼：

- `specs/backend/stock-price-ingestion.md`（行情抓取與回補）
- `specs/backend/stock-universe-import.md`（上市股票清單與產業別匯入）
- `specs/backend/stock-catalog.md`（股票清單查詢與人工維護）
- `specs/backend/stock-indicator-statistics.md`（MACD／KD 指標運算與統計）
- `specs/backend/stock-minute-price.md`（分鐘 K 棒隨選抓取）
- `specs/backend/industry-gain-ranking.md`（產業別漲幅排行）
- `specs/backend/strategy-scan.md`（策略型態掃描）
- `specs/backend/strategy-backtest.md`（策略命中回測）

整合後的樣貌是：系統核心只有**兩份真正的資料**——「股票有哪些」與「股票每天收盤多少」——其餘一切（分鐘 K、技術指標、產業別分組、型態掃描、命中回測）都是建立在這兩份資料之上、依不同角度加工出來的**衍生結果或即時運算**，其中型態掃描、產業別漲幅排行、策略命中回測三個功能完全不落地任何自己的資料表，每次呼叫都是重新計算。系統不存在需要人工審核的待審流程；「進度未完成」（`PENDING`／`RUNNING`／`FAILED`）指的是背景作業還沒跑完，不是等人核准。

## 3. 每個 entity / data store 的角色

### 3.1 股票主檔

<img src="backend/1-stock.png" width="320" alt="股票主檔在完整架構圖中的位置">

*（節錄自完整架構圖）*

`stock` 是全系統唯一的「這檔股票存不存在、叫什麼名字、在哪個市場掛牌、目前還在不在市面上」的地方。它有三條各自獨立的維護路徑：交易所每日全市場行情發布時順帶更新代號與名稱；使用者按「更新股票清單」時一次性補齊全市場普通股並帶入產業別；操作人員也可以手動新增、改名或下市單一標的。三條路徑刻意分工不重疊——自動路徑**永遠不會**把一檔股票標記為下市、也不會把已被人工下市的股票改回在市，是否在市完全交給人工決定。下市是**軟刪除**：只把在市狀態改為否，既有的行情與指標歷史一列都不動，代號本身也不可經由修改端點更動（它是行情、指標、進度三份資料共同依附的鍵）。

詳細欄位、規則與 API 定義 → docs/backend/stock-catalog.md

### 3.2 日線行情

<img src="backend/1-price.png" width="320" alt="日線行情在完整架構圖中的位置">

*（節錄自完整架構圖）*

`stock_daily_price` 是全系統唯一的行情落地表，也是指標運算、型態掃描、產業別漲幅排行、策略回測共同的輸入來源——沒有任何功能會另外對外抓價格。它有四條抓取路徑：每個交易日的例行更新（單一請求涵蓋全市場當日行情）、系統初次建置時的全市場逐日回補（主路徑，每個交易日一次請求涵蓋全市場）、指定少數標的的逐檔歷史回補（同時也是逐日回補來源被封鎖時的降級路徑），以及系統啟動完成後自動觸發、把每一檔在市普通股補到今日的啟動補齊。逐檔路徑背後有 Yahoo 為主、FinMind 為備援的雙來源，任一來源被判定封鎖時自動切換到另一個，不會把封鎖期內的標的判定為失敗。所有寫入一律使用可重複執行的覆寫寫法，停牌或無交易的日期不補零、不留列。

詳細欄位、規則與 API 定義 → docs/backend/stock-price-ingestion.md

### 3.3 分鐘 K 棒

<img src="backend/1-minute.png" width="320" alt="分鐘 K 棒在完整架構圖中的位置">

*（節錄自完整架構圖）*

`stock_minute_price`（含其抓取狀態）服務的是使用者點開某一檔股票某一個交易日時要看的盤中走勢，抓取方式與日線完全不同——不是排程主動全抓，而是**隨點選隨抓、抓過即永久保存**，因為使用者實際會看的組合遠小於全市場全歷史的量級。依日期分由兩個互不備援的來源負責：最近 30 天由 Yahoo 抓、更早（但不早於一個可設定的最早日期）由富果 Fugle 補抓，早於這個最早日期一律直接回報「超出範圍」而不對外發出任何請求。已經抓到並存起來的日期即使日後超過來源的 30 天視窗，仍直接讀資料庫，不會改由另一個來源重抓。

詳細欄位、規則與 API 定義 → docs/backend/stock-minute-price.md

### 3.4 MACD／KD 指標

<img src="backend/1-indicator.png" width="320" alt="MACD／KD 指標在完整架構圖中的位置">

*（節錄自完整架構圖）*

`stock_daily_indicator` 是由日線行情**遞迴推導**出來的技術指標序列，本系統一律自行計算、不從任何外部服務取得指標數值。運算分兩種模式：全量重建（從很久以前的暖身區間整條重算，用於全新標的或參數變動）與每日增量（讀前一交易日的遞迴狀態推進一步）。這兩種模式**不是由呼叫端指定整批統一使用哪一種**，而是逐檔依「這檔目前有沒有指標列」自動判斷；若增量推進時發現序列出現缺口（找不到前一日的狀態），該檔會被標記為需要改走全量重建，避免用假設的初始值污染後續所有日期。系統啟動把行情補齊之後，會自動對全市場觸發一次指標重算，不需要人工介入。

詳細欄位、規則與 API 定義 → docs/backend/stock-indicator-statistics.md

### 3.5 產業別

<img src="backend/1-industry.png" width="320" alt="產業別在完整架構圖中的位置">

*（節錄自完整架構圖）*

`industry` 是一份以中文名稱為唯一鍵的產業分類字典，本表**只增不刪**，即使某個分類名稱之後不再被任何股票使用也不會被移除。它與股票之間的分類關聯（原始為一張純粹的關聯表）由「更新股票清單」這個動作以**整組取代**的方式維護，但取代的範圍嚴格限定在**這一次來源實際涵蓋到的股票**——沒有出現在本次來源清單裡的股票（例如人工新增、或該次來源剛好漏掉的標的），其既有分類關聯完全不動，不會被清空。產業別的匯入與股票清單的匯入是同一個使用者動作的兩半，但兩者的失敗處理不對稱：股票清單來源失敗會讓整個動作視為沒有成功、不寫入任何資料；產業別來源失敗則不影響股票清單已經匯入的結果，只是誠實回報這次的分類沒有更新。

詳細欄位、規則與 API 定義 → docs/backend/stock-universe-import.md

### 3.6 同步進度追蹤

<img src="backend/1-progress.png" width="320" alt="同步進度追蹤在完整架構圖中的位置">

*（節錄自完整架構圖）*

`stock_sync_progress` 是一份與具體業務內容無關的通用進度表，記錄「某一種背景作業、對某一檔標的，現在跑到哪個狀態、失敗過幾次、進度到哪一天」，同時被行情回補與指標重算兩種作業共用（以作業種類區分，彼此的併發鎖互不影響）。它存在的目的是讓長時間、會中斷的批次作業能夠安全地續傳、不重複浪費外部請求，也讓「重試次數過多」有一個煞車機制，避免一檔真正有問題的標的把整批作業卡死。它是否知道自己在追蹤「行情」還是「指標」完全不重要——這正是它能被兩種作業共用而不用複製一份的原因，詳見第 4 節。

詳細欄位、規則與 API 定義 → docs/backend/stock-price-ingestion.md

## 4. 通用模組：同步進度追蹤的 contract 設計

`stock_sync_progress` 對它所追蹤的「作業」內容一無所知，這是它能被行情回補與指標重算兩種完全不同的業務邏輯共用的關鍵設計。它的 contract 只有幾個通用欄位：作業種類、標的代號、狀態（等待中／執行中／已完成／失敗／已跳過）、已重試次數、以及「補到哪一天了」。任何新的背景批次作業，只要願意遵守這組狀態語意，就能直接沿用整套續傳、節流、重試上限的機制，不需要另寫一套。

幾個不直觀但重要的行為規則：**外部來源被判定封鎖造成的中止，不會被算成一次失敗嘗試**——因為那不是這檔標的本身有問題，若算進重試次數，一次來源端的暫時性封鎖就可能把全市場標的一起推過重試上限；**已完成的標的可以被重新打開**——如果它「完成」的進度已經落後於這次要求補到的日期，系統會自動重新開啟它並只補落後的那一段，重試次數也會歸零重算，因為落後是時間往前走造成的，不是先前失敗的延續。

## 5. End-to-End 情境走查

**情境一：從一個只有種子資料的空資料庫，開機到系統真正可用。** 系統啟動完成後，先以交易所每日行情把股票主檔的代號與名稱補齊到近千檔的完整上市清單，緊接著自動把每一檔在市普通股的日線行情補到今日；行情批次全部結束後（不是同時進行），再自動對全市場觸發一次指標重算——尚無指標的新標的走全量、已有指標的標的走增量。這三個階段依序發生、缺一步都會讓使用者看到「有 K 棒但沒有指標」或「清單裡只有 34 檔開發樣本」的不完整畫面，且全程都靠同步進度追蹤保證重複啟動不會重複浪費外部請求。

**情境二：使用者按「更新股票清單」，再按「同步日 K 至今日」，最後做策略掃描與回測。** 更新股票清單只補齊「有哪些股票」與「屬於哪個產業」，刻意不寫任何一天的行情，避免行情表出現一根沒有前後文的孤立資料，破壞指標的遞迴推導；接著使用者要自己按下同步日 K，才會真正把歷史行情補齊；型態掃描與命中回測則完全建立在已經補齊的行情之上做即時運算，不會自動觸發任何回補——如果使用者跳過同步日K就直接掃描，掃描到的只會是空的或不完整的行情。

**情境三：全市場逐日行情來源被交易所判定封鎖時的降級與自動恢復。** 全市場回補的主要作法是逐日跟交易所要當日全市場的行情，一旦這個管道被封鎖，系統不會讓整批作業失敗，而是自動改用速度較慢、但仍受雙來源保護的逐檔查詢方式繼續把剩下的標的補完；封鎖到期之後，下一次作業會自動改回原本的主要作法，不需要人工介入或重啟。降級期間寫入的行情筆數上會留下痕跡（來源不同），供事後辨識，但價格本身不會因為換了抓法而不一致。

**情境四：策略掃描命中「上漲支撐」型態後，回測用的並不是訊號當天的價格。** 「上漲支撐」這個型態要等到訊號日之後兩個交易日都守住起漲價才算真正成立，因此掃描回報的「可以進場的那一天」與「型態出現訊號的那一天」是刻意不同的兩個日期；命中回測固定以掃描回報的進場日收盤價買進，而不是訊號當天，避免用還沒發生的未來資訊挑股票、讓回測績效被系統性美化。這條規則若被忽略，會讓「上漲支撐」這個型態的回測報酬率看起來比實際能操作到的更好。
