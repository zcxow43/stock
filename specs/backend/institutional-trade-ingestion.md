# 三大法人買賣超抓取與補齊 — Backend Spec

## Overview

`specs/backend/strategy-scan.md` 的三個法人籌碼型態（法人買賣超佔比、法人連續買超、法人買超強度排名）需要逐檔逐日的外資與投信買賣超股數。現有的四個行情來源（`STOCK_DAY_ALL`、MI_INDEX、Yahoo、FinMind，見 `specs/backend/stock-price-ingestion.md`）都不提供這項資料。本模組自交易所三大法人買賣超日報抓取，寫入 `stock_institutional_trade`（見 `specs/dba/stock-institutional-trade.md`）。

請求成本的單位與日線全市場回補相同：**每個交易日 1 次請求**，與母體有多少檔無關。

**本模組沒有對外端點，也沒有進度表。** 它是日線抓取的附屬步驟，觸發時機跟著日線走（見「觸發時機」）；而「哪些日期還沒抓」可以直接由資料本身回答（見「缺少日期的認定」），不需要另一份可能與資料不一致的進度紀錄。使用者不需要任何新按鈕——策略分頁既有的「同步日 K 至今日」同時帶動法人資料。

## Requirements

### 資料源（已測事實）

| 項目 | 值 |
|---|---|
| 端點 | `https://www.twse.com.tw/rwd/zh/fund/T86?date=<YYYYMMDD>&selectType=ALLBUT0999&response=json` |
| 涵蓋 | 指定某一交易日、全體上市證券（`ALLBUT0999`：全部，不含權證、牛熊證） |
| 請求數 | 每個交易日 1 次 |
| 需要 token | 否 |

以 `date=20260911` 實測確認：

- `stat` 為 `"OK"`，`hints` 為 `"單位：股"`。
- `fields` 共 19 欄：`證券代號`／`證券名稱`／`外陸資買進股數(不含外資自營商)`／`外陸資賣出股數(不含外資自營商)`／`外陸資買賣超股數(不含外資自營商)`／`外資自營商買進股數`／`外資自營商賣出股數`／`外資自營商買賣超股數`／`投信買進股數`／`投信賣出股數`／`投信買賣超股數`／`自營商買賣超股數`／`自營商買進股數(自行買賣)`／`自營商賣出股數(自行買賣)`／`自營商買賣超股數(自行買賣)`／`自營商買進股數(避險)`／`自營商賣出股數(避險)`／`自營商買賣超股數(避險)`／`三大法人買賣超股數`。
- `data` 共 **1,008 列**，含 ETF（例如 `00632R`）。主檔的上市證券約 1,368 檔——**資料源只列出當日有法人交易的證券**，沒被列出的代表當日三類法人均無買賣。
- 數值為帶千分位符號的字串，買賣超可為負（`-69,992,000`）。
- **單位為「股」**，與 `stock_daily_price.volume` 相同（依 `.claude/rules/backend.md`，另以驗收項對真實資料核對，見 Acceptance Criteria）。

以 `date=20260913`（週日）實測非交易日：回應為 `{"stat":"很抱歉，沒有符合條件的資料!","total":0}`，**不含 `fields` 與 `data`**。

**未實測**：交易日收盤後、日報尚未發布時請求的回應形狀。依非交易日的形狀推測相同，但不作為前提——下方「失敗處置」以「`stat` 不為 `OK`、或沒有 `data`」涵蓋兩者，不依賴它們長得一樣。

#### 解析規則

- **以 `fields` 的欄名定位每一欄，不得以陣列索引取值。** 這與 MI_INDEX「以 `fields[0]` 定位個股行情表」是同一個教訓：欄位順序一旦調整，以索引取值不會拋錯，只會把投信的數字寫進外資的欄位。上表 19 個欄名中缺少任一個 → 視為格式錯誤（見「失敗處置」）。
- 證券代號去除前後空白後使用。
- 數值沿用日線抓取既有的千分位／佔位符正規化處理，**不另寫一套解析**。
- 欄名與資料表欄位的對應見 `specs/dba/stock-institutional-trade.md` 的「資料源欄位對應」。

### 缺少日期的認定

一個日期**需要抓**，當且僅當同時成立：

1. 它是**交易日**：`stock_daily_price` 在該日至少有一列；且
2. `stock_institutional_trade` 在該日**沒有任何一列**。

**以日線的交易日為準，而不是逐個日曆日請求。** 日線的逐日回補必須逐日曆日問，因為哪一天是交易日要由資料源回答（見 `specs/backend/stock-price-ingestion.md` 的「逐日回補的處理流程」）；而到了本模組執行的時候，日線已經回答過這個問題了。直接沿用它，週末與假日一次都不會被請求。反過來，若逐日曆日請求，每次補齊都會對區間內的每一個假日重發請求，而且永遠補不到——假日沒有列可寫，下次仍判定為缺少。

**以「該日有沒有任何一列」判定已抓取，而不另建進度表。** 交易日只要有交易，資料源就會列出上千檔，一個成功寫入的交易日不可能是零列；反過來，零列的交易日就是還沒抓到（未發布、請求失敗、作業中斷）。「有列＝已抓」這個判斷與資料永遠一致。另一張進度表則可能出現「進度說抓過了，表裡卻沒有資料」的狀態，而那正是補齊要修正的情形。

這個判斷成立的前提是**單日的列必須整批寫入或整批不寫**（見「寫入」）。

**尚未發布與尚未抓取，在這個判定下沒有差別。** 收盤後日報尚未發布時請求，不會寫入任何列，該日下一次觸發時會再被請求一次。代價是每次觸發多一次請求，理由與日線 spec 的「`last_synced_date` 的認定」相同：為了省這一次請求去維護一份發布時間表，不值得。

### 補齊範圍

- 區間為 **`[日線補齊起日, 今日]`**。起日沿用 `specs/backend/stock-price-ingestion.md` 的「補齊起日」設定（預設 `2026-01-01`），**不另設一個起日**。法人資料早於日線的部分沒有用（佔比與強度要以成交量為分母），晚於日線則會讓區間前段的股票全部落入資料不足。
- 缺少的日期由舊到新逐日處理。

### 寫入

- **只寫入 `stock` 主檔中已存在的代號**，不論 `is_active`、不論是否為普通股；主檔不存在的代號一律丟棄，**不新增主檔列**。只寫主檔內的代號，理由與日線逐日快照相同：universe 只由主檔同步維護，多一條寫主檔的路徑正是分類與 `is_active` 最容易悄悄不一致的成因。不以普通股過濾，是因為掃描可以帶 `commonStocksOnly: false` 或指名 ETF，那時需要它們的資料。
- `source` 寫入 `TWSE`，以 UPSERT 寫入。
- **單日的全部列在同一個交易邊界內寫入。** 寫到一半中斷、留下部分列的日期，會被「有列＝已抓」判定為已完成，缺的那幾百檔之後永遠不會被補。
- 某日的回應經主檔過濾後為零列（實務上不會發生），視同未抓，不寫入。

### 觸發時機

在**背景非同步**觸發一次補齊。觸發點有兩個：

1. **每一次 `PRICE_BACKFILL` 作業結束時**——不論它是啟動補齊、策略分頁的「同步日 K 至今日」，還是手動呼叫回補端點。「結束」包含：全部標的已是最新而未發出任何外部請求就結束的情形，以及有部分標的失敗的情形（已寫入的交易日照樣可以補法人資料）。
2. **每日增量（`POST /api/stocks/sync/daily`）成功寫入之後。**

規範：

- **兩條日線路徑的 API 回應內容與回應時間都不因此改變。** 補齊一律在背景執行，是日線作業的附屬步驟，不是它對外行為的一部分。
- **同一時間只跑一個補齊。** 觸發時已有補齊在執行 → 本次觸發直接略過，記錄一行資訊紀錄，不排隊。執行中的那一個結束後若仍有缺少的日期，下一次觸發自然會補上；排隊只會讓同一段日期被連續查兩次。
- **跟著日線觸發，而不是自己排程**：「缺少日期」的定義依賴日線，日線沒寫入的交易日，本模組本來就不會去抓。日線剛寫入的那一刻，正是新交易日出現的那一刻。
- 當日日報稍晚才發布時，使用者再按一次「同步日 K 至今日」即可補上：日線已是最新、該回補作業不發外部請求就結束，結束時照樣觸發本補齊。

設定項（實際鍵名與檔案格式由 `env.md` 的技術棧決定）：

| 設定 | 預設 | 說明 |
|---|---|---|
| 法人資料補齊開關 | 啟用 | 關閉時兩個觸發點都不發出任何 T86 請求。**測試與 CI 必須能關掉它**，理由同日線的啟動補齊：測試打真實外部 API，結果會取決於外部服務是否可用 |

### 速率控制

- **與 MI_INDEX 共用同一道請求間隔閘門，封鎖狀態也共用。** 兩者是同一個主機（`www.twse.com.tw`）的端點，而封鎖是這個主機對本機 IP 施加的。若各自計時，兩者同時運作時對同一主機的實際請求密度會加倍。日線 spec「節流的單位是來源」這條規則在這裡的正確解讀是：來源＝會對我們施加封鎖的那一方，也就是主機。
- 間隔值沿用 MI_INDEX 的設定，不另訂一組。
- 逐日循序處理，不並行。理由同日線逐日路徑：請求數以交易日計，並行只是讓多個工作者一起排隊等同一道閘門。

### 失敗處置

| 情形 | 處置 |
|---|---|
| `stat` 不為 `OK`，或回應沒有 `data`／`data` 為空（非交易日、尚未發布） | 不寫入、不記為失敗，繼續下一日 |
| `403`／`429`，或回應內容指出封鎖 | **立即結束本次補齊**，記錄錯誤，把該主機標記為不可用（MI_INDEX 同時看得到）。**不重試**：下一次觸發本來就會補上剩下的日期，重試只是對一個正在封鎖的主機多送請求 |
| 逾時、`5xx` | 沿用日線既有的指數退避重試；重試用盡後跳過該日並記錄錯誤，繼續下一日 |
| 格式錯誤（缺少必要欄名、數值無法解析） | 該日整日不寫入，記錄錯誤，繼續下一日 |

- **補齊的任何失敗都不影響日線作業的結果、進度或 API 回應**，也絕不讓應用程式啟動失敗。開發機在離線狀態下仍須能開起來。

### 時區

所有日期為台北日曆日，與 `specs/backend/stock-price-ingestion.md` 的「時區」一致。

## Implementation Details

### 處理流程

觸發 → 開關未啟用則結束 → 已有補齊執行中則略過並記錄 → 區間取 `[補齊起日, 今日]` → **以一次查詢**取得缺少日期（`stock_daily_price` 在區間內的相異交易日，扣除 `stock_institutional_trade` 在區間內的相異交易日）→ 由舊到新逐日：經共用閘門請求 T86 → 依「失敗處置」分流 → 以欄名定位各欄、正規化、以主檔過濾代號 → 單一交易邊界 UPSERT → 下一日 → 全部處理完畢後記錄一行摘要（缺少日數／寫入日數／無資料日數／失敗日數）。

缺少日期必須以一次查詢求出，不得對區間內每個日期各查一次。

## Acceptance Criteria

### 解析與寫入
- [ ] 以 `date=20260911` 的真實回應寫入後，抽查 `2609`（陽明）一列：`foreign_buy_shares = 46546290`、`foreign_sell_shares = 23548005`、`foreign_net_shares = 22998285`、`trust_net_shares = 102106`、`total_net_shares = 23747702`，其餘欄位亦與回應逐欄一致
- [ ] 賣超寫入為負值：`00632R` 的 `foreign_net_shares = -69992000`
- [ ] 單位核對（股，不是張）：以真實資料取同一交易日若干檔，`foreign_buy_shares + foreign_dealer_buy_shares + trust_buy_shares + dealer_self_buy_shares + dealer_hedge_buy_shares` 不超過同日 `stock_daily_price.volume`，且至少一檔的比值落在 `0.01`～`1` 之間（若單位為張，比值會小約 1000 倍）
- [ ] 以欄名定位：把同一份回應的 `fields` 與 `data` 各欄同步打亂順序後解析，寫入結果與原順序完全相同
- [ ] `fields` 缺少任一必要欄名的構造回應 → 該日零列寫入、記錄錯誤、下一日照常處理
- [ ] 非交易日形狀的回應（`{"stat":"很抱歉，沒有符合條件的資料!","total":0}`）→ 不寫入、不記為失敗
- [ ] 主檔不存在的代號不寫入，且 `stock` 列數不變；主檔中的 ETF 與 `is_active = 0` 的代號照常寫入
- [ ] 寫入的列 `source` 為 `TWSE`
- [ ] 同一日重跑兩次：列數不變，第二次的值覆蓋第一次
- [ ] 單日寫入在單一交易邊界：模擬寫到一半失敗 → 該日在 `stock_institutional_trade` 為零列，下一次觸發時重新請求該日

### 缺少日期與補齊範圍
- [ ] 構造 `stock_daily_price` 在區間內有 3 個交易日、`stock_institutional_trade` 已有其中 1 日 → 本次補齊恰發出 **2** 次 T86 請求
- [ ] 區間內的週末與休市日（`stock_daily_price` 無列的日期）一次都不請求
- [ ] 所有交易日都已有法人資料時觸發 → **0** 次外部請求
- [ ] 缺少日期以單一查詢求出，查詢次數不隨區間日數增加
- [ ] 區間起日取自日線的「補齊起日」設定，改動該設定後本補齊的起日隨之改變

### 觸發
- [ ] `PRICE_BACKFILL` 作業結束後自動觸發一次補齊，包含 `caughtUpCount == targetCount`（未發任何外部請求）與有部分標的 `FAILED` 的情形
- [ ] 每日增量成功後自動觸發一次補齊
- [ ] 回補端點的 `202` 回應與每日增量的 `200` 回應，欄位與值皆與未加本功能前相同，且不等待補齊完成才回應
- [ ] 補齊執行中再次觸發 → 本次略過並留下資訊紀錄，同一時間不存在兩個補齊，也不排隊重跑
- [ ] 開關關閉時，兩個觸發點都不發出任何 T86 請求；測試環境的設定預設為關閉

### 速率控制與失敗
- [ ] 與 MI_INDEX 共用請求間隔：兩者交錯執行時，對 `www.twse.com.tw` 的相鄰兩次請求間隔不小於設定值
- [ ] T86 回 `403`／`429` → 本次補齊立即結束且不重試；MI_INDEX 隨即看到該主機為不可用；剩餘日期於下一次觸發時補上
- [ ] 逾時 → 依退避重試，用盡後跳過該日並繼續處理下一日
- [ ] 補齊失敗時，日線作業的狀態、進度與 API 回應皆不受影響；外部網路不通時應用程式仍正常啟動
